### ✅ P0-05 建立共享磁盘缓存容量与保留空间算法

- 交付：提供纯策略模型，以“当前可用空间减必须保留空间”为新增缓存上限，区分缓存已用、可新增、用户限额和安全下限。
- 直接收益：让 EXO 与 MPV 使用同一安全语义，避免把卷总容量比例误当成仍可写空间。
- 风险预览：保留值过大时缓存命中率下降，过小时仍可能挤满磁盘；不同卷和异常文件系统返回值需防溢出。

### ✅ P0-06 EXO 磁盘缓存接入保留空间并处理写满

- 交付：`MediaSourceFactory` 使用 `P0-05` 容量策略；空间不足或 ENOSPC 时停止新增/预载、清理可回收项并保持前台播放可恢复。
- 直接收益：降低 SimpleCache 侵占保留空间和磁盘写满造成播放失败的概率。
- 风险预览：SimpleCache 容量在活动会话中不能随意重建；错误处理过度可能导致缓存反复释放。
- 验收重点：容量延迟切换状态机、活动会话、空间骤降和写失败路径均被覆盖。
- 依赖：`P0-05`。
- 实施结果：删除 EXO 原“缓存已用与可用空间之和的 80%”容量公式，改用共享保留空间策略和 `StatFs` 可用/总容量事实；活动会话持续使用创建时的真实 evictor 容量，安全上限下降或配置变化时暂停预载，等全部 EXO 会话退出后重建 `SimpleCache`，由 Media3 LRU 回收超限 span。存储事实不可用时禁止预载但保留已有缓存容量，安全上限未下降时允许满缓存做等量 LRU 置换；前台数据源继续禁止边播边写并忽略缓存读取错误。新增独立存储暂停状态和单媒体会话磁盘熔断，仅识别 `CacheDataSinkException`、ENOSPC、`No space left on device`、`errno 28`，普通 HTTP/超时错误不误判；熔断只停止预载，不中断前台播放，日志不记录异常正文或 URL。
- 验证：新增/扩展 17 个专项用例，覆盖容量归零与扩容、多会话释放顺序、满缓存 LRU 置换、安全上限下降、需回收、存储事实不可用、配置关闭、直接/嵌套 ENOSPC、普通网络错误、异常链循环和存储事实边界；共享缓存与 EXO 相关共 32 个测试类、151 个单测通过，失败/错误/跳过均为 0；Mobile arm64 Debug 单测变体及 Leanback arm64 Debug Java 编译通过，`git diff --check` 通过。当前没有可控满盘设备，ENOSPC 仅完成异常注入测试；真机空间骤降、实际 `SimpleCache` 写满后的 LRU 回收和前台连续播放仍待设备端到端验证。

- 验收重点：并发读写、活跃对象保护、清理顺序、写失败和直通回退测试。
- 依赖：`P0-05`。
- 实施结果：新增进程级 `MpvHlsCacheCoordinator`，按 `mpv_hls` 规范路径让 MPV/IJK 共享同一组容量、写入预留、缓存键、活动读取引用、LRU 清理和 ENOSPC 熔断状态；当前活动内核采用最保守的正容量配置，关闭某一内核不会清空共享目录。协调器接入 `DiskCacheCapacityPolicy` 与 `FileUtil` 的真实 `StatFs` 信息，容量核算包含完整文件、`.tmp`/元数据实际占用和所有并发写入的剩余预留，预留在写入进度、成功提交、失败、取消和响应关闭的所有出口释放。存储事实不可用、保留空间不足或共享熔断时禁止新写入和预取，但已有完整文件仍可读取；前台缓存写入失败会丢弃缓存分支并继续上游直通。ENOSPC 仅打开共享写入熔断、取消后续预取并回收安全 LRU 对象，普通 HTTP/超时错误不误触发；同键只允许一个提交者，活动读取文件不会被删除，提交使用同目录原子重命名，启动时回收过期临时文件。缓存保护日志只记录异常类型、容量状态和处理动作，不记录 URL、路径或异常正文；同一协调器也覆盖代理内的 DASH 分片写入。
- 验证：新增 12 个协调器专项用例，覆盖共享实例、最保守内核容量、完整/临时文件计量、并发预留及释放、活动读取保护与 LRU、同键竞争、成功/竞争原子提交、存储事实不可用时读写分离、ENOSPC 熔断/恢复、普通写入错误、嵌套 `errno 28` 和遗留文件回收；Mobile arm64 与 Leanback arm64 Debug 单测各 407 个通过（失败/错误/跳过均为 0），Leanback arm64 Debug Java 编译通过，`git diff --check` 通过。当前没有可控满盘设备，ENOSPC、直通回退和预取停止仅完成异常注入/代码路径验证；真机满盘、实际上游 Range 差异及长时连续播放仍待设备端到端验证。

### ✅ E-10 实现 EXO RTSP live lag 恢复

- 交付：检测落后直播边缘和异常增长，按能力跳最新位置或重建会话，并设置冷却和重试上限。
- 收益：避免 RTSP 卡顿后持续播放历史内容并积累内存。
- 风险预览：live edge 不可靠时跳转会丢内容；频繁重建可能造成连接风暴。
- 依赖：`F-02`、`F-06`。
- 实施结果：新增纯 `ExoRtspLiveLagPolicy` 和按完整 SessionToken 隔离的 `ExoRtspLiveLagController`，直接复用 F-02 请求/engine 合并分类和 F-06 约 5 秒运行采样。只有 EXO 自动档、协议明确为 RTSP、分类与 `isCurrentMediaItemLive()` 共同确认 live、首帧或音频已可播且仍有 playWhenReady 的会话才记录证据；非 EXO、非自动档、HLS/DASH、RTSP VOD、UNKNOWN、暂停、用户 Seek、位置不连续、错误、资源替换和旧会话均 HOLD 并清除旧样本。
- 实施结果：30 秒以上 live lag 视为超限；15 秒以上且每秒继续增加至少 500ms 视为异常落后。普通风险至少需要 3 个样本和 10 秒持续确认，120 秒以上的紧急风险仍需要 2 个样本和 5 秒，避免单次回调或短时抖动触发。`getCurrentLiveOffset()` 不可用时不猜 live edge，只在 `getTotalBufferedDuration()` 已达 90 秒且每秒继续增长至少 500ms 时，把它作为异常队列增长代理并只允许重建；该值不是 native RSS、服务端绝对时间或内存泄漏证明。

### ✅ M-02 按事实运行时扩缩 MPV forward cache

- 实施结果：critical 和安全容量下降立即缩容；MODERATE 每个压力阶段只降一层，重复/乱序事件不会连续棘轮。需求下降至少需 2 个运行样本且稳定 10 秒，每次只降一层；普通扩容要求可信需求稳定至少 20 秒、新鲜 NORMAL pressure 与可用 snapshot，并且每 15 秒最多升一层。压力恢复至少需要 2 个新鲜 NORMAL 内存样本和 30 秒稳定窗口，critical 冷却 60 秒，moderate/容量下降冷却 30 秒；即使当时媒体需求很低也不会提前清除 critical 冷却，防止后续码率升高绕过恢复期。UNKNOWN、过期或重复事实只能保持或收紧。

- 验证：新增/扩展 26 个 M-02 专项用例，覆盖需求公式、Format 优先与 runtime fallback、下载速度不作为需求、LOW/过期事实、未知内存基线、64/96/128/192MiB 容量门槛、low-RAM/小 heap/低 headroom、critical、local/live/opaque cap、扩容/降容迟滞、MODERATE 去棘轮、容量继续下降、critical 恢复、低需求不提前解除冷却、重建目标恢复、失败重试、会话隔离以及 6 个 native 白名单层级。Mobile arm64 与 Leanback arm64 Debug 全量单测各 780 个通过（失败/错误/跳过均为 0），两变体 Debug APK 构建通过，`git diff --check` 通过。ADB 无连接设备，未进行真实 MPV 高码率长播、运行属性读回、缩容后 `fw/total` 收敛、native packet pool、RSS/PSS 回落、lowMemory/LMK 或 context 替换端到端验证。

### ✅ M-03 按向后 Seek 行为自动管理 MPV back cache

- 交付：默认 0；满足真实回看行为和内存余量后逐步启用 16/32/64MiB，直播、无 Seek 或压力时归零。

- 风险预览：首次向后 Seek 可能重新请求网络；forward 可借用 back，统计必须按潜在总量计算。
- 依赖：`M-02`、`F-06`。
- 实施结果：新增纯 `MpvBackCachePolicy` 和按完整 `SessionToken` 隔离的 `MpvBackCacheController`。默认 back=0，只接受 Media3 `DISCONTINUITY_REASON_SEEK`、同一媒体项、旧位置大于新位置且后退至少 5 秒的事件；向前 Seek、相等位置、小于 5 秒抖动、媒体项切换、未知位置和 `SEEK_ADJUSTMENT` 均不形成回看证据。10 分钟证据窗口内第一次真实后退只记录行为，第二次学习 16MiB、第三次 32MiB、第四次及以上 64MiB；第一次大幅后退仍不立即占内存，已有一次证据后的 60 秒以上大幅后退可加快学习，但每次实际扩张仍只升一层且间隔至少 30 秒。10 分钟没有新的有效向后 Seek 会清除证据并把 back 归零。

- 实施结果：新增会话级 `MpvCacheTargetCoordinator`，M-02 forward 与 M-03 back 的任何变更都通过同一次受限调用组合提交两个 byte 目标，避免 forward 更新把 back 写回 0、back 更新覆盖 forward、重复提交或同会话重建丢失目标。控制器先在各自同步状态机和组合协调器中提交动作，随后全部离锁调用 MPV；成功、失败、暂存、重试、旧 SessionToken、新会话清零和 release 均隔离。同会话 MPV context 重建即使尚未重新获得 Timeline，也会恢复此前已批准且仍满足当前事实的组合值；新媒体会话重新从 back=0 学习。native 自动选项层进一步只接受 0/16/32/64MiB back，仍只拥有 `demuxer-max-back-bytes` 与 `demuxer-max-bytes`。
- 实施结果：新增 `mpv-back-cache` 与组合目标日志，最多记录 Seek 方向/距离证据数、学习层、安全 back、潜在总预算、forward 目标、MPV observer 的实际 `fw-bytes/total-bytes`、压力、稳定样本、冷却和动作，不记录 URL、host、路径或异常正文。源码语义以仓库内 bundled mpv `94335ab87` 为准：back=0 会严格关闭历史包保留，默认 donation 只让 back 使用未占用的 forward 空间，潜在总量仍按 forward+back 计算；运行时缩小总上限会触发旧包裁剪并可能清理 packet pool，但 setter/暂存成功仍不代表属性已读回、裁剪已完成或 RSS 立即下降。

### ✅ M-04 消除 MPV 缓存时间参数重复语义

- 交付：明确 `cache-secs` 与 `demuxer-readahead-secs` 的单一主控关系，并以小规模实验评估 hysteresis。
- 收益：减少配置互相覆盖，让日志展示值与实际行为一致，并可能降低持续唤醒功耗。
- 风险预览：hysteresis 过大可能放大网络突发；不同 demuxer 对时间目标响应不一致。
- 依赖：`M-02`。
- 实施结果：以仓库内 bundled mpv `94335ab87` 为准，cache 启用时 native 实际使用 `max(cache-secs, demuxer-readahead-secs)`。现已把当前通常 15～30 秒、策略边界兼容至 60 秒的档位目标只交给 `cache-secs`，`demuxer-readahead-secs` 恢复为 native 默认 1 秒，仅作为 cache 未启用时的 demuxer fallback，不再把同一个 30 秒目标写入两项。推荐、兼容、轻量和自定义性能优先档同样消除重复语义但 hysteresis 保持 0；`mpv.conf优先` 不进行运行时覆盖，仍由用户配置决定三个时间选项。
- 实施结果：新增纯 `MpvCacheTimePolicy`。hysteresis 首轮只开放给 MPV 自动档、请求分类明确为 progressive HTTP 且播放器路径明确为远程直连或 LAN 的连续传输；15/30/60 秒 cache 目标分别只尝试 4/5/6 秒，并要求该阈值至少比 `cache-pause-wait` 多 2 秒，否则回到 0。HLS、DASH 因加载前无法可靠区分 VOD/live/LL-live，RTSP/RTMP、本地、应用内服务、外部 loopback、未知协议/路径以及较高重缓冲等待全部保持 hysteresis=0；没有直接采用官方示例 10 秒，也没有把 4～6 秒描述为平台最佳值。

### ✅ I-01 用清单和时间线识别 IJK VOD/live/LL-live

- 交付：不再只看 URL scheme；解析 HLS `ENDLIST`、target/part duration、hold-back，并为无法判断场景保留 unknown。
- 收益：普通 HTTP HLS 直播可获得正确的低延迟和有限缓存策略。
- 风险预览：代理改写或不规范清单可能缺失标签；unknown 必须采用安全回退。
- 依赖：`P0-01`、`F-02`。
- 实施结果：扩展共享资源分类器，新增 `PLAYLIST-TYPE`、`PART-TARGET`、实际 Part `DURATION`、普通 `HOLD-BACK` 与 `PART-HOLD-BACK` 的独立解析；`CAN-BLOCK-RELOAD=YES` 单独出现不再误判 LL-HLS，明确 `PLAYLIST-TYPE:VOD` 但尚无 `ENDLIST` 时保持 unknown，EVENT 收到 `ENDLIST` 后再转为 VOD。LL-HLS live offset 优先使用 `PART-HOLD-BACK`，缺失时使用约 3 个 part；普通 live 优先使用 `HOLD-BACK`，缺失时使用约 3 个 target duration。
