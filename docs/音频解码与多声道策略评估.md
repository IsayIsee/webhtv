# 音频解码与多声道策略评估

## 评估范围

本文基于当前 WebHTV 的 Exo 和 MPV 播放路径、已有任务文档及设备验证记录，评估以下问题：

1. 软解并输出 PCM 时，多声道音频是否始终保持原始多声道。
2. 当前音频处理是否严格遵循以下优先级：
   原格式精确直通 -> DSP compressed offload -> 原音轨硬件 MediaCodec 解码并输出 PCM -> 同轨兼容格式 -> 原音轨软件解码 PCM -> 同语言兼容音轨或 2.0 音轨。

本文是只读评估记录，不代表本次已经修改实现。特殊格式和具体设备组合仍需通过真实设备矩阵验证。

## 一、软解与 PCM 的多声道结论

### 总结

不能确认“软解 + PCM 时所有多声道都能正常保持多声道”。更准确的判断是：

```text
标准 5.1/7.1 + 目标 AudioTrack 支持对应布局：通常保持多声道 PCM。
目标路由不支持对应布局：可能下混为 2.0。
未知布局、超过 8 声道或特殊 AV3A：可能下混，也可能初始化失败。
```
此外，PCM 只表示输出编码形式，不代表电视内置扬声器、蓝牙设备或音频 HAL 最终一定以多声道物理播放；最终路由仍可能把 PCM 下混为 2.0。

### Exo

`CompatFfmpegAudioRenderer` 会检查目标 `AudioTrack` 是否支持源声道数、声道 mask 和采样率：

- 目标路由支持源布局时，通常保留源声道数并输出对应多声道 PCM。
- 源声道数大于 2、目标不支持原布局但支持 stereo 时，会在解码器侧下混为 2.0。
- 源布局和 stereo 都不支持时，renderer 可能不声明可处理，随后触发其他 renderer 或轨道回退。
- 声道数、声道 mask 与解码器实际输出不一致时，不能把文件声明的声道数当作实际输出保证。

当前已知的 AV3A 风险是：文件可能声明 6 声道，但 `libarcdav3a` 实际产生未知布局的 9 声道，已有 `swr_init` 失败及 9->6/2 处理问题记录。现有 DASH 声道配置可达性修复不等于所有 AV3A 多声道组合已经验证通过。

参考：[CompatFfmpegAudioRenderer.java](/Users/macbookpro/Desktop/github/webhtv/app/src/main/java/io/github/anilbeesetti/nextlib/media3ext/ffdecoder/CompatFfmpegAudioRenderer.java:134)

### MPV

MPV 的 `ao_audiotrack` 标准声道 mask 映射主要覆盖到 7.1，最多 8 声道：

- 常见 5.1/7.1 在目标 `AudioTrack` 支持时可以保持多声道 PCM。
- 超过 8 声道时，当前实现会强制改成 stereo。
- 未知多声道布局转 stereo 时，`f_swresample` 使用显式 matrix 下混，优先保证可播放，但不再是原始多声道输出。
- `multichannelPcm` 默认关闭；无法直通时，MPV 可能在解码前选择同语言的 stereo 音轨，而不是继续使用当前多声道轨道。

参考：[mpv-audiotrack-compressed-audio.patch](/Users/macbookpro/Desktop/github/webhtv/third_party/patches/mpv-audiotrack-compressed-audio.patch:734)、[MpvDirectAudioPolicy.java](/Users/macbookpro/Desktop/github/webhtv/app/src/main/java/com/fongmi/android/tv/player/mpv/MpvDirectAudioPolicy.java:14)

## 二、六级音频顺序评估

### 总体结论

六级顺序本身合理，当前实现也已经覆盖了主要降级路径，但 Exo 和 MPV 尚未形成统一、严格、无条件的 1->6 状态机。因此当前应评为“部分达标、可用但未完全闭环”，而不是“完全按顺序执行”。

| 优先级 | 当前实现判断 |
| --- | --- |
| 1. 原格式精确直通 | Exo、MPV 都受用户开关和实际路由能力约束；AudioTrack 初始化或写入失败后可回退，基本符合。 |
| 2. DSP compressed offload | 主要覆盖纯音频和特定设备、格式、采样率、声道组合，不是所有压缩格式的通用路径，部分符合。 |
| 3. 原格式硬件 MediaCodec -> PCM | Exo 有硬件候选优先和初始化失败回退；但“音频软解优先”设置会把 FFmpeg renderer 插到平台 MediaCodec 前面。MPV 的 AAC/MP3/AMR 基本是硬件优先，失败后回到软件解码。 |
| 4. 同轨兼容格式 | MPV 有明确的一次性 DTS-HD -> DTS Core 回退；Exo 没有发现对等的通用同轨兼容格式策略。 |
| 5. 原音轨软件解码 PCM | 两者都有，但 Exo 会受“音频软解优先”设置影响；MPV 还可能受 `multichannelPcm` 设置影响而先换轨。 |
| 6. 同语言兼容或 2.0 音轨 | MPV 有明确的同语言 stereo/较低复杂度选择，但主要限于 `mediacodec_embed` 路径；Exo 主要依赖 Media3 默认选轨，没有发现同等明确的应用层最后降级策略。 |

### 关键偏差

1. **Exo 的软解优先设置会改变第 3 和第 5 级顺序。** 这是有意提供的用户覆盖，但默认产品策略不能同时宣称硬件始终优先。

   参考：[ExoUtil.java](/Users/macbookpro/Desktop/github/webhtv/app/src/main/java/com/fongmi/android/tv/player/exo/ExoUtil.java:869)

2. **DSP compressed offload 覆盖范围有限。** Media3 标准 offload 受纯音频、独立 audio renderer、格式和设备能力等条件约束；视频带音频时通常不会进入标准 offload。厂商 direct encoded 路径也只覆盖已确认的格式和采样率/声道组合。

3. **Exo 缺少与 MPV 对等的同轨兼容格式降级。** MPV 已有 DTS-HD 失败后一次性降级 DTS Core，Exo 主要依赖 renderer/PCM fallback、MIME 兼容和默认选轨。

4. **MPV 的最后换轨策略受视频输出路径限制。** `maybeSelectPreferredDirectAudio()` 只在 `mediacodec_embed` 路径执行，GPU/OpenGL/Vulkan 路径不一定执行同样的第 6 级策略。

   参考：[MpvPlayer.java](/Users/macbookpro/Desktop/github/webhtv/app/src/main/java/androidx/media3/mpvplayer/MpvPlayer.java:4129)

5. **MPV 默认关闭 `multichannelPcm`。** 这会使无法直通的多声道轨道优先让位给同语言 stereo/较低复杂度音轨，符合“最后降级”的可播放性目标，但不符合“尽量保留当前多声道原音轨”的目标。

6. **两套播放器的第 6 级没有统一。** MPV 有应用层策略，Exo 没有发现对等、明确且可观测的统一策略。

## 三、当前成熟度判断

当前实现已经比较合理，具备较好的日常可用性，不属于架构错误或需要推倒重来：

- 常见 AAC、MP3 和标准 5.1 播放路径基本成熟。
- 直通失败后的同轨 PCM 回退设计实用。
- MPV 的 DTS-HD -> DTS Core 回退能够覆盖重要的兼容场景。
- V2453A 已有 AAC 硬件尝试失败后回退软件 PCM 的设备证据。

但它还不能称为“非常优秀、完全闭环”：

- 不能保证所有多声道始终原声道输出。
- Exo 与 MPV 的优先级和最后降级策略不完全一致。
- AV3A、未知布局、超过 8 声道和特定输出路由仍有风险。
- DSP offload 和 Exo 同轨兼容格式降级尚未形成完整覆盖。

## 四、建议的优化优先级

### P0：明确并统一策略契约

定义 Exo 与 MPV 共享的音频决策顺序和可观测结果：每一级都记录尝试、成功、失败原因和下一步，避免把“用户软解优先”“设备不支持”“输出路由下混”混为同一种结果。

验收重点：默认配置下硬件 MediaCodec 不被软件 renderer 无意抢先；用户显式开启软解优先时，行为和界面状态清晰可解释。

### P1：补齐 Exo 同轨兼容格式回退

为 Exo 增加与 MPV 对齐的一次性同轨兼容格式策略，例如 DTS-HD 失败后尝试 DTS Core；回退必须绑定当前轨道和当前失败原因，避免换轨循环、重复初始化或无条件牺牲音质。

### P1：统一最后降级策略

将 MPV 的同语言 stereo/较低复杂度选择与 Exo 的轨道选择策略抽象为同一产品规则，并确保 `mediacodec_embed`、GPU、OpenGL、Vulkan 等路径行为一致或明确记录差异。

### P1：处理多声道布局边界

对未知布局、超过 8 声道、AV3A 5.1/7.1/7.1.4 等组合明确选择：保留原布局、显式矩阵下混或失败后换轨。不能只依据文件声明的声道数判断成功。

### P2：建立最小真实设备验证矩阵

至少覆盖：

- Exo 与 MPV 的 AAC、MP3、DTS/DTS-HD、AV3A；
- 2.0、5.1、7.1 及代表性的高声道布局；
- 原格式直通成功、直通失败回退 PCM、硬件 MediaCodec 不可用回退软件；
- 电视内置扬声器、HDMI 功放、蓝牙等不同输出路由；
- `multichannelPcm` 开关及 MPV 不同视频输出路径。

验证应同时记录解码器、AudioTrack 实际声道 mask、采样率、输出编码、是否发生下混和最终选中的音轨。

## 五、最终结论

```text
当前版本可以继续使用，基础设计合理，日常播放能力较好。
但若目标是严格实现 1->6 的统一顺序，或对外宣称所有多声道都能保持原声道，当前仍明显缺少闭环。
下一步应优先统一决策状态机、补齐 Exo 的同轨兼容降级、统一最后换轨策略，并用真实设备验证 AV3A 和高声道边界。
```
